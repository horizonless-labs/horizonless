# PRD 0001: v0.1, Horizon-style payments and operations from Stellar RPC

Labels: `ready-for-agent`
Status: ready · 2026-10-15
Design summary: see `docs/SPEC.md`

## Problem Statement

Stellar's Horizon API "is nearing end-of-life" and "won't receive new feature development". Developers are told to move to Stellar RPC. Many Stellar apps are built on Horizon's ready-made views, especially wallets, exchanges, payment processors, anchors and accounting tools:

- "payments for this account"
- "operations in this transaction"
- "what moved where, in what asset, for how much"

RPC doesn't offer those views. The official migration guide says per-transaction payments and effects have "No direct RPC equivalent; use getEvents or parse getTransactions". The fallback, classic-asset events, only appears when the RPC operator turns on `EMIT_CLASSIC_EVENTS`, so developers can't count on it across providers.

Every team migrating today has to decode transaction envelopes, results and metadata themselves. They have to work out Horizon's field rules (amounts as 7-decimal strings, asset type/code/issuer splitting, path-payment source and destination amounts, operation IDs) and keep their stored cursors and IDs compatible. The only reference implementations are in Go. That work is error-prone, gets repeated across the ecosystem, and is hard to test once Horizon is gone.

## Solution

`horizonless` is a TypeScript library. It takes transactions fetched from Stellar RPC and returns records with exactly the same shape and values Horizon returns for the same transaction.

- **v0.1 covers Horizon's payments view** for the five classic payment-type operations: `create_account`, `payment`, `path_payment_strict_send`, `path_payment_strict_receive` and `account_merge`.
- **It also provides a matching operations view for those same operations,** plus a helper that walks RPC transactions over a ledger range and yields payment records, optionally filtered to one account.
- **Records are built from the transaction envelope and result,** which is how Horizon builds them. They don't depend on whether the RPC provider emits classic events.
- **Record IDs and paging tokens are identical to Horizon's,** so stored cursors and database keys keep working after migration.
- **Correctness is shown, not claimed:** every supported case has a recorded real transaction whose output must equal Horizon's recorded answer.

## User Stories

1. As a wallet developer migrating off Horizon, I want to turn an RPC transaction into Horizon-shaped payment records, so that my transaction-history screen keeps working without a rewrite.
2. As a wallet developer, I want the payment records to have exactly Horizon's field names and value formats, so that my existing types, serializers and UI code need no changes.
3. As an exchange engineer, I want each record's `id` and `paging_token` to equal Horizon's, so that the cursors and primary keys already in my database stay valid.
4. As an exchange engineer watching deposits, I want to get every incoming payment to a given account across a ledger range, so that I can credit customer deposits from RPC alone.
5. As a payment processor, I want path payments to report both the amount actually sent and the amount received, so that I can reconcile cross-asset payments correctly.
6. As a payment processor, I want `path_payment_strict_send` records to include `destination_min` and `path_payment_strict_receive` records to include `source_max`, so that I can audit slippage limits the same way I did on Horizon.
7. As a payment processor, I want path-payment records to list the intermediate path assets in order, so that I can explain conversion routes to customers and auditors.
8. As an anchor operator, I want `create_account` records with funder, new account and starting balance, so that I can track accounts I've sponsored or funded.
9. As an anchor operator, I want `account_merge` records with the merged account and the destination, so that I can detect when customer accounts are closed into another account.
10. As a developer, I want XLM records to say `asset_type: native` with no code or issuer, and issued-asset records to carry `asset_type`, `asset_code` and `asset_issuer`, so that asset handling matches Horizon.
11. As a developer, I want both 4-character and 12-character asset codes handled, so that every issued asset on the network works.
12. As a developer, I want amounts as decimal strings with seven places (for example `"10.0000000"`), so that I never lose precision to floating-point numbers and my formatting matches Horizon.
13. As a developer, I want each record to carry `transaction_hash`, `transaction_successful`, `source_account`, `created_at`, `type` and `type_i`, so that every record links back to its transaction and can be sorted and filtered like Horizon's.
14. As a developer, I want an operation with no source account of its own to report the transaction's source account, so that `source_account` matches Horizon's.
15. As a developer, I want failed transactions excluded by default and included only when I opt in, so that the default behaviour matches Horizon's `/payments`.
16. As a developer handling fee-bump transactions, I want the inner transaction's operations converted correctly, so that sponsored-fee payments aren't lost or misattributed.
17. As a developer, I want a transaction that mixes payment and non-payment operations to return only the payment records, keeping each one's correct position-based ID, so that output and IDs match Horizon.
18. As a developer, I want an operations view for the same five operation types, so that I can rebuild Horizon's `/operations` for transactions I care about.
19. As a developer, I want to pass either the SDK's parsed transaction object or the raw JSON-RPC result, so that the library works whether I use the SDK client or my own HTTP calls.
20. As a developer on `@stellar/stellar-sdk` 17 or later, I want the library to share my SDK version instead of bundling its own, so that I don't get duplicate or conflicting XDR types.
21. As a developer, I want the conversion functions to be pure and synchronous with no network access, so that I can use them in workers, edge runtimes, tests and batch jobs.
22. As a developer, I want the streaming helper to accept any client that can fetch pages of transactions, so that I can use the SDK's server, my own RPC wrapper, or a test fake.
23. As a developer, I want the streaming helper to page through results until the range or the RPC's latest ledger is reached, so that I don't have to write paging loops.
24. As a developer, I want the streaming helper to filter by account, matching either the sender or the receiver, so that I only process payments that involve my account.
25. As a developer, I want a clear, typed error when I pass something that isn't an RPC transaction, or a transaction that isn't found, so that integration mistakes surface immediately.
26. As a developer, I want unsupported operation types skipped quietly in the payments view, so that new or uncommon operations never crash my pipeline.
27. As a developer, I want full TypeScript types for every record kind, distinguished by `type`, so that my editor narrows fields correctly per operation.
28. As a developer, I want the package to work with both ESM and CommonJS, so that it fits modern and legacy Node projects.
29. As a developer evaluating the library, I want a README with a 30-second example and a Horizon-to-horizonless mapping table, so that I can judge fit in minutes.
30. As a contributor, I want a documented recipe for adding an operation type (capture a test transaction, add a mapper, register it, run the tests), so that I can deliver a scoped issue without learning the whole codebase.
31. As a contributor, I want a script that captures a test case from any transaction hash, recording both the RPC response and Horizon's answer, so that I can add new test cases without hand-writing JSON.
32. As a contributor, I want the test suite to run offline from committed test cases, so that my PR checks are fast, deterministic, and don't depend on testnet uptime or RPC's 7-day history limit.
33. As a maintainer, I want a scheduled live check that converts recent testnet transactions and reports any mismatch with Horizon, so that real-world edge cases turn into new issues instead of silent bugs.
34. As a maintainer, I want CI to run lint, typecheck, tests and build on every PR, so that contributor PRs from bounty programs are judged on objective signals.
35. As a maintainer, I want versioned releases with changelogs and verifiable npm publishing, so that users can trust and pin the package.
36. As a Wave organizer reviewing the repo, I want to see a well-scoped backlog of issues, each with a clear acceptance test, so that I can tell the project is ready for contributors.
37. As a security-conscious user, I want the library to never need secret keys and never make network calls from the conversion functions, so that it's safe to run on untrusted data in a backend.

## Implementation Decisions

**Modules**

- **Input normaliser.** Accepts either the SDK's parsed transaction (SDK ≥ 17 uses plain snake_case XDR objects) or the raw JSON-RPC result (base64 XDR strings), and produces one internal shape: envelope, result, ledger sequence, ledger close time, application order, success flag and fee-bump flag. This is the only module that knows about SDK object formats, so SDK changes are contained here.
- **ID builder.** Computes Horizon's operation ID (TOID): ledger sequence in the top 32 bits, transaction application order (1-based) in the next 20 bits, and operation index (1-based) in the low 12 bits. The result is a decimal string. `paging_token` equals `id`.
- **Shared record builder.** Fills the fields common to every record: id, paging token, transaction hash, success flag, source account (operation source or else transaction source), created-at (ISO-8601 UTC from ledger close time), type name and numeric type.
- **Asset and amount formatter.** Converts XDR assets to Horizon's `asset_type` / `asset_code` / `asset_issuer` fields (with the prefix variants `source_asset_*`), and converts 64-bit stroop amounts to seven-decimal strings with no float maths.
- **Per-operation mappers.** One small mapper per supported operation type, registered in a type-keyed registry. Each mapper receives the normalised operation, its result, and the shared record, and returns the Horizon-shaped record. Path-payment mappers read the amounts actually sent or received from the operation result. Adding an operation type means adding one mapper and one registry entry.
- **Public façade.** `toPayments` returns records for payment-type operations only. `toOperations` returns records for every operation with a registered mapper. Both are pure and synchronous, and both take an option to include failed transactions (default: exclude).
- **Streaming helper.** An async iterator over a minimal client interface: anything with a `getTransactions` method taking a start ledger or cursor and a limit. It pages until it reaches the requested end or the latest ledger, converts each transaction with the façade, and optionally filters by account, matching either party. The SDK's RPC server satisfies this interface without an adapter.

**Contracts**

- **Output types** are Horizon's response schemas for each record type, without `_links`, as a union discriminated by `type`.
- **Horizon is the reference.** Wherever this spec and Horizon's behaviour differ, Horizon's behaviour wins. Field presence, order-independent equality and string formats are all checked against recorded Horizon output.
- **Muxed-account fields are left out in v0.1.** Records use the base account (`G…`) address wherever Horizon would also expose muxed variants. That gap is tracked as a follow-up issue.
- **Errors:** a typed error for input that can't be recognised as an RPC transaction, and a typed error for a transaction RPC reports as not found. Unsupported operation types are skipped, never thrown.

**Architecture and packaging**

- Single npm package, Apache-2.0 licence.
- `@stellar/stellar-sdk` ≥ 17 is a peer dependency, with no other runtime dependencies.
- Dual ESM and CommonJS build, with type declarations.
- Port the logic from Horizon's operations processor (now in the `stellar-horizon` repo) rather than writing it fresh, and note the source in each mapper's doc comment.
- Classic unified events (`transfer`/`mint`/`burn`) aren't used to build records in v0.1. A cross-check mode is planned separately.

**Verified facts behind these decisions (2026-10-15)**

- SDF's public testnet RPC returns `TransactionMetaV4`, with per-operation ledger changes, for classic transactions.
- That same RPC currently includes classic `transfer`/`burn` events. Other providers may not.
- Horizon's `account_merge` payment record doesn't include the merged amount, so v0.1 leaves it out too.

## Testing Decisions

**What makes a good test here.** Tests only exercise public behaviour: given a recorded RPC transaction, the public function's output must deep-equal Horizon's recorded answer for the same transaction hash. Tests never import internal modules. When a mapper or formatter is wrong, a test case fails at the public seam, and the diff shows exactly which field is wrong.

**Seam 1 (main): `toPayments` / `toOperations`.**
- Each test case is a directory holding the RPC `getTransaction` response plus Horizon's `/transactions/{hash}/payments` and `/transactions/{hash}/operations` responses, captured at the same time.
- One table-driven test loops over every test case and compares output with `_links` stripped.
- v0.1 needs at least one test case per operation type, plus:
  - an issued asset with a 12-character code
  - a failed transaction (with and without the include option)
  - a fee-bump transaction
  - a multi-operation transaction that mixes payment and non-payment operations
  - a path payment with a non-empty path

**Seam 2: `streamPayments`.**
- Tests inject a fake client that serves recorded `getTransactions` pages.
- They check paging until the end, stopping at the latest ledger, account filtering on both sender and receiver, and that output order and IDs match the per-transaction results.

**Test-case capture tool.** A script records a new test case from a network name and transaction hash. Test cases are committed and permanent, since RPC only keeps about 7 days of history and testnet resets.

**Offline CI.** No test touches the network. A separate scheduled job converts recent testnet transactions live and reports mismatches. It's informational and never blocks merges.

**Prior art.** This is a new repo with no existing tests. The pattern copies Horizon's own approach of checking processors against known ledger data, and the recorded-response testing common to SDK clients.

## Out of Scope

- Effects (`/effects`): planned for v0.2.
- Trades, offers and liquidity-pool views.
- `invoke_host_function` and Stellar Asset Contract transfers in the payments view.
- Muxed-account fields (`*_muxed`, `*_muxed_id`).
- Operation types beyond the five payment-type ones (offers, trustlines, options, claimable balances, sponsorship, clawback): each becomes a backlog issue.
- Cross-checking against classic unified events.
- Persisting history, indexing, or any HTTP server or Horizon-compatible REST API (a possible separate project).
- Account balances or state views (Horizon's `/accounts`).
- Browser bundle size work. The library should work in browsers, but v0.1 doesn't optimise for them.

## Further Notes

- The project is aimed at the Drips Stellar Wave. The follow-up backlog (around 18 issues covering operation types, effects, muxed fields, event cross-check and docs examples) should be opened as soon as the repo is public, with each issue's acceptance criterion being "this new test case passes".
- If SDF starts building equivalent functionality in js-stellar-sdk, the library should stay API-compatible enough to upstream or wrap it. As of 2026-10-15, no such issue or PR exists.
- Horizon remaining live is what lets us record its answers. Capture a broad set of test cases early, before any shutdown.
